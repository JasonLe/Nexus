# 08 - 配置系统

> 模块路径：`nexus/cli/config.py`
> 教学视角：配置系统看似「基础设施」，实则是框架「可扩展性」的第一道门槛。理解五级配置优先级、ProviderConfig 的抽象设计，就能明白 Nexus 如何做到「同一套代码，切换不同模型、不同工具集」。

---

## 1. 设计目标

Nexus 的配置系统需要解决三个核心问题：

1. **多环境适配**：开发机、CI、生产环境使用不同的 API Key 和模型
2. **团队协作**：项目级配置共享（如默认模型、系统提示词），个人级配置隔离（如 API Key）
3. **动态调整**：运行时修改配置并热生效（通过 Server 的 PUT /api/config）

## 2. 配置数据模型

### 2.1 核心数据类

[`nexus/cli/config.py`](file:///Users/wanghanle/Documents/code/githubProject/Nexus/nexus/cli/config.py) 使用 `@dataclass` 定义了层次化的配置结构：

```python
@dataclass
class ProviderConfig:
    """单个 LLM Provider 的配置。"""
    api_key: str | None = None
    model: str = ""
    max_tokens: int = 4096
    context_window_tokens: int = 0   # 0 = 未知/不启用自动截断
    base_url: str | None = None

@dataclass
class AgentConfig:
    """Agent 级别的配置。"""
    system_prompt: str = "You are a helpful coding assistant."
    max_steps: int = 30

@dataclass
class ToolsConfig:
    """工具启用配置。"""
    enabled: list[str] = field(default_factory=list)
    # 空列表 = 全部启用（默认行为）
    # ['__none__'] = 全部禁用（哨兵值）

@dataclass
class MCPServerConfig:
    """单个 MCP Server 的配置。"""
    command: str | None = None
    args: list[str] = field(default_factory=list)
    env: dict[str, str] = field(default_factory=dict)
    url: str | None = None
    enabled: bool = True

@dataclass
class NexusConfig:
    """聚合配置 —— 完整配置文件的内存表示。"""
    providers: dict[str, ProviderConfig] = field(default_factory=dict)
    default_provider: str = "openai"
    agent: AgentConfig = field(default_factory=AgentConfig)
    tools: ToolsConfig = field(default_factory=ToolsConfig)
    mcp_servers: dict[str, MCPServerConfig] = field(default_factory=dict)
    stream: bool = True
    
    # 运行时字段（不从配置文件加载）
    verbose: bool = False
    debug: bool = False
    work_dir: str = ""
    log_dir: str = ""
```

### 2.2 便捷属性

`NexusConfig` 提供了一组 `@property` 便捷访问器，避免调用方频繁遍历 `providers`：

```python
@property
def provider_config(self) -> ProviderConfig:
    """当前 provider 的配置。"""
    return self.providers.get(self.default_provider, ProviderConfig())

@property
def model(self) -> str:
    """当前生效的模型名称。"""
    return self.provider_config.model

@property
def api_key(self) -> str | None:
    """当前 provider 的 API Key。"""
    return self.provider_config.api_key
```

**教学点**：这种「聚合根 + 便捷属性」的设计模式，让上层代码（如 factory.py）只需关心 `config.model`、`config.api_key`，而不需要知道 Provider 的内部结构。

## 3. 五级配置加载优先级

```python
def load_config(cli_args=None, work_dir=None) -> NexusConfig:
    """合并五级配置来源（后加载覆盖前加载）：
    
    1. 代码默认值
    2. 用户级配置 ~/.nexus/nexus.yaml（向后兼容 ~/.nexus/config.json）
    3. 项目级配置 —— 从 work_dir 向上查找 nexus.yaml 直到 .git 边界
    4. 环境变量（NEXUS_MODEL / NEXUS_API_KEY / NEXUS_PROVIDER 等）
    5. 命令行参数（cli_args），最高优先级
    """
```

### 3.1 各级配置详解

| 优先级 | 来源 | 加载方式 | 典型用途 |
|--------|------|----------|----------|
| 1 | 代码默认值 | 硬编码 | 内置 provider 列表（openai/anthropic/minimax） |
| 2 | 用户级 YAML | `~/.nexus/nexus.yaml` | 个人 API Key、偏好模型 |
| 3 | 项目级 YAML | 从 `work_dir` 向上查找至 `.git` 边界 | 项目专属系统提示词、工具配置 |
| 4 | 环境变量 | `NEXUS_*` 前缀 | CI/CD 注入敏感信息 |
| 5 | 命令行参数 | `--model`, `--provider` 等 | 临时覆盖 |

### 3.2 项目级配置的向上查找

```python
def _find_project_config(start_dir: str, filename: str) -> str | None:
    """从 start_dir 向上查找配置文件，遇到 .git 边界停止。
    
    查找顺序：start_dir → parent → ... 直至遇到目标文件、
    .git 目录（项目根边界）或文件系统根。
    """
    current = Path(start_dir).resolve()
    for parent in [current] + list(current.parents):
        candidate = parent / filename
        if candidate.is_file():
            return str(candidate)
        if (parent / ".git").exists():
            return None
    return None
```

**教学点**：为什么要向上查找？
- 开发时可能在项目子目录中运行 `nexus`
- 向上查找确保无论 cwd 在哪里，都能读到项目根的配置
- `.git` 作为边界，避免跨项目污染配置

## 5. 配置保存

### 5.1 save_config() 实现

```python
def save_config(config: NexusConfig, path: str | None = None) -> str:
    """将配置持久化为 YAML 文件。
    
    写入策略：
    - 生成结构化 YAML，不含空值
    - api_key 保留（用户手动管理的配置需要可持久化）
    - 文件权限设为 0o600（仅属主可读写，降低明文 key 风险）
    """
```

### 5.2 安全设计

```python
# 配置文件可能包含明文 api_key，限制为属主可读写（POSIX 生效）
try:
    os.chmod(path, 0o600)
except OSError:
    pass
```

### 5.3 工具配置的持久化规则

```python
# tools 始终保存（包括 enabled=[] 表示全部启用、['__none__'] 表示全部禁用）
data["tools"] = {"enabled": list(config.tools.enabled)}
```

**教学点**：为什么 `enabled=[]` 也要持久化？
- 早期 bug：enabled 为空时不保存，重启后工具状态丢失
- 修复后：无论 enabled 是什么值，都无条件写入 YAML
- 这是「配置即状态」原则的体现

### 6.2 api_key 的掩码与合并

```python
def _mask_api_key(api_key: str | None) -> tuple[bool, str | None]:
    """掩码规则：保留前 3 位 + **** + 后 4 位。"""
    return has_key, "sk-****abcd"

def _merge_config_json(config, data):
    new_key = prov.get("api_key")
    if new_key and new_key != current_mask:
        pc.api_key = new_key  # 传新值 → 更新
    # 传掩码值 → 不修改（避免误覆盖明文 key）
```

**教学点**：掩码机制是前后端协作的关键契约：
1. 后端 GET /api/config 返回掩码值
2. 前端展示掩码值，用户未修改时回传相同掩码值
3. 后端判断「回传值 == 当前掩码」→ 不修改对应字段

## 7. 项目级 vs 用户级配置边界

| 维度 | 用户级 `~/.nexus/nexus.yaml` | 项目级 `./nexus.yaml` |
|------|------------------------------|----------------------|
| 内容 | API Key、个人偏好模型 | 系统提示词、工具列表、MCP 配置 |
| 版本控制 | ❌ 不提交（含敏感信息） | ✅ 可提交（团队共享） |
| 加载时机 | 先加载 | 后加载（覆盖用户级） |
| `tools` 字段 | ❌ 不应包含（会覆盖用户配置） | ❌ 不应包含 |

**重要约束**：项目级 `nexus.yaml` **不应包含 `tools` 字段**，否则加载时会覆盖用户级的工具配置，导致用户自定义的工具启用状态丢失。

## 9. 扩展指南

### 添加新的 Provider

1. 在 `_default_providers()` 中添加默认配置
2. 在 `create_llm()` 中添加 Provider 工厂分支
3. 用户可在 `nexus.yaml` 中配置新 Provider 的参数

### 添加新的配置字段

1. 在对应的数据类（如 `AgentConfig`）中添加字段
2. 在 `load_config` 的合并逻辑中处理新字段
3. 在 `save_config` 中序列化新字段
4. 在 `_config_to_json` 中添加 API 暴露（如需前端展示）
